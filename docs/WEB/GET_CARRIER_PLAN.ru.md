# Telemt WEB proxy через GET-only CDN — план работ

Репозиторий: https://github.com/Rerowros/telemt (форк telemt/telemt, база `main` @ 9d5b896, ≈ 3.5.14).
Ветка для работы: `feat/web-get-carrier`. Результат — PR в этот форк (не в upstream).

## 1. Зачем

Telegram Desktop 7.1+ умеет прокси типа **WEB** (`tg://webproxy?server=HOST&secret=dd…`). Telemt в WEB-режиме
принимает его за nginx. Сейчас у нас:

```
relay.example.com  → RU VPS (nginx TLS) → origin nginx :8443 → telemt WEB 127.0.0.1:18080   — РАБОТАЕТ
cdn.example.com  → Yandex Cloud CDN   → origin nginx :8443 → telemt WEB 127.0.0.1:18080   — НЕ РАБОТАЕТ
```

cdn-хост не работает, потому что **Yandex Cloud CDN пропускает только GET**, а весь WEB-протокол telemt
(`/api/v1/session`, `/up`, `/down`) — это POST/PUT/DELETE. Нужно научить telemt (и страницу-мост, которую
он сам отдаёт клиенту) работать **только GET-запросами**. Тогда любой GET-only CDN становится входом,
который нельзя заблокировать по IP без побочного ущерба.

## 2. Измеренные факты (09.10.2026, проверено вручную через cdn-хост)

Yandex Cloud CDN:
- POST с телом → `413 Request Entity Too Large`; PUT/DELETE/OPTIONS тоже не проходят.
  Включить методы нельзя: API отвечает `method "POST" management is unavailable for resource`.
- GET проходит. Кеш на ресурсе выключен (`disableCache`), query string **не игнорируется**.
- Длина URL: 8 000 символов в query — 200, 12 000 — `414`. **Бюджет на URL ≤ 7 500 байт.**
- Один заголовок: 8 000 байт — 200, 16 000 — `400`. Суммарный лимит заголовков не мерили — считать ≤ 8 КБ.
- Запрос → origin доходят без изменений: `Authorization: Bearer …`, `X-Up-Seq`, `X-Lane-ID`, `Content-Type`,
  query string целиком. `Host` = публичный хост (cdn.example.com). `X-Forwarded-For` = **один** IP клиента.
- Ответ → клиенту доходят нестандартные заголовки (`X-Session-Token`, `X-Down-Cursor`, `Cache-Control`).
- НЕ проверено: держит ли CDN GET-ответ 25–30 с (long-poll `/down`) и не режет ли его по таймауту.
  Косвенно — да (VLESS XHTTP через этот же CDN работает с долгими ответами). Проверить на шаге 0.
- WebSocket через CDN не проверяли и **не используем**.

Клиент Telegram Desktop (`Telegram/SourceFiles/mtproto/web_proxy/`, tdesktop):
- WebView открывается только на точный URL моста `https://HOST/?bridge=…` (`WebviewCarrier::validNavigation`),
  сообщения принимаются только со страницы того же https-хоста, порт 443, тот же путь (`validSource`),
  `restrictedOrigin = https://HOST`.
- Клиент **не проверяет** содержимое/хеш страницы и не диктует HTTP-методы: сеть делает JS моста,
  который отдаёт наш сервер. Значит, менять транспорт моста можно, клиент это не сломает.
- Режим «Open browser» встраивает тот же мост в iframe — тоже наш код.

## 3. Что сделать (дизайн)

### 3.1 Конфиг
- Расширить `WebCarrierMethod` (`src/config/types/web_carrier.rs`): `post` (по умолчанию), `put`, **`get`**.
- Добавить **переопределение на уровне vhost**: `[[web.vhosts]] carrier_method = "get"` (без него — значение
  из `[web]`). Нам нужно: cdn-хост = `get`, relay-хост = `post` в одном процессе.
- Новый лимит `web.limits.get_url_bytes` (по умолчанию 7168): максимум длины URL, который мост генерирует.
- Валидация конфига: `get` совместим только с carrier `https` и `https-lanes` (не websocket*); hot-reload — как у
  существующего `carrier_method`.

### 3.2 Мост (JS в `src/web/bridge/*.js`, сборка в `src/web/bridge.rs`)
Политика метода уже «page-owned» (см. `carrier_method` и `request.js → options()`), режим GET добавляется туда же:
- Все обращения `/api/v1/session` (создание и закрытие), `/up`, `/down` идут как `GET`.
- Тело запроса (если есть) → query-параметр `d` в **base64url без паддинга**. Токен и служебные заголовки
  (`X-Up-Seq`, `X-Down-Cursor`, `X-Lane-ID`, `X-Carrier-*`) можно оставить заголовками (CDN их пропускает),
  но для устойчивости к другим CDN — дублировать в query (`t`, `s`, `c`, `l`…). Выбор зафиксировать в коде одним
  местом.
- Закрытие сессии (сейчас `DELETE /api/v1/session`) → `GET /api/v1/session?op=close&…`.
- Каждый запрос получает уникальный параметр (`n` = счётчик/nonce), `cache: 'no-store'` уже стоит — оставить.
- **Фрагментация аплинка.** Uplink-тело бывает до `max_body_bytes` (2 МБ), а в URL влезает ~5 КБ сырых данных.
  Делить одно логическое тело на части: `p=i`, `pn=N` при одном и том же `X-Up-Seq`. Сервер склеивает части и
  обрабатывает тело ровно так же, как один POST. Части отправлять последовательно (сохранить порядок), повтор —
  той же частью (идемпотентно по `seq,i`).
- Даунлинк (`/down`) — GET без тела, long-poll как сейчас; ограничений по размеру ответа нет.
- Существующие таймауты/ретраи/recovery не менять, кроме бюджета на ретраи с учётом N частей.

### 3.3 Сервер (`src/web/http/*.rs`)
- В `http.rs`/`request.rs`: если у vhost `carrier_method = get`, принимать `GET` на carrier-путях и
  **до существующих обработчиков** превращать запрос в канонический вид (метод, тело из `d`, заголовки из query).
  Дальше работают те же `session.rs`, `up.rs`, `down.rs` — логику протокола не дублировать.
- Буфер склейки фрагментов: на сессию, по `X-Up-Seq`; ограничен `max_body_bytes` и учитывается в
  `memory_envelope` / budget (`src/web/manager/budget.rs`). Таймаут недосборки = `bridge_request_secs`,
  затем буфер выбрасывается. Повтор уже принятой части — без ошибки.
- Строгая проверка формы: кривой base64, лишние/повторные параметры, части не по порядку, `pn` больше лимита,
  смесь GET+тело и т. п. → тот же ответ, что сейчас для неверных запросов (decoy / закрытие стрима), **без**
  новых наблюдаемых отличий для неавторизованных запросов (см. принцип decoy в docs/WEB/WEB_PROXY.en.md).
- POST/PUT на vhost с `get` — оставить рабочими (нужно для отладки и смешанных клиентов).
- Ответы: `Cache-Control: no-store` на всех carrier-ответах (проверить, что уже так).

### 3.4 Что не трогать
- MTProto/ME-часть, другие транспорты, websocket-carriers, существующие тесты (только добавлять).
- Формат ссылки `tg://webproxy` и вычисление capability.

## 4. Тесты (обязательно)
- Rust unit/integration рядом с существующими (`src/web/http/carrier_method_tests.rs`,
  `src/config/tests/load_basic_tests/web_tests/carrier_method_tests.rs`, `src/web/bridge/tests.rs`):
  - конфиг: `get` глобально и per-vhost; несовместимые сочетания отклоняются;
  - GET-сессия создаётся, uplink/downlink проходят, закрытие через `op=close`;
  - фрагментация: 1 часть, N частей, повтор части, части не по порядку, недосборка по таймауту,
    превышение лимита;
  - неверные формы → поведение как у неавторизованных запросов (decoy), счётчики не портятся;
  - на vhost без `get` GET carrier-пути по-прежнему отклоняются.
- **E2E с имитацией CDN**: локальный nginx перед telemt, который режет всё кроме GET (`limit_except GET`),
  отдаёт `414` при URL > 8 КБ и `400` при заголовке > 8 КБ; headless-браузер (Playwright) открывает мост,
  подставляет фейковый «нативный» порт (как это делает tdesktop через `postMessage`) и гоняет поток данных
  туда-обратно, включая аплинк 1 МБ (проверка фрагментации) и long-poll 30 с.
- `cargo test`, `cargo clippy -- -D warnings`, `cargo fmt --check` зелёные.

## 5. Шаг 0 и приёмка (делает владелец/оператор, не Devin — у Devin нет доступа к серверам)
1. Сборка: бинарь `x86_64-unknown-linux-gnu` (сервер — Ubuntu, сейчас там telemt 3.5.6) через GitHub Actions
   форка как артефакт релиза.
2. На origin-сервере заменяется **только** `/opt/telemt-web/telemt` (отдельный экземпляр WEB), остальные telemt не
   трогаются. Конфиг: `[[web.vhosts]] host = "cdn.example.com"` → `carrier_method = "get"`.
   Учесть изменения конфига между 3.5.6 и базой форка (лимиты `web.limits` валидируются строже).
3. Проверка long-poll через CDN (25–30 с) и реальное подключение Telegram Desktop 7.1.2+ через cdn-хост
   (из России). Метрики: время подключения, загрузка фото, стабильность > 1 ч.

## 6. Критерии готовности
- Telegram Desktop подключается через `cdn.example.com` (Yandex CDN, только GET) и работает > 1 ч:
  сообщения, приём медиа, отправка фото до 5 МБ.
- relay-хост (POST) продолжает работать на том же процессе.
- Все тесты из п. 4 есть и зелёные; PR описывает формат GET-запросов (параметры, лимиты, фрагментация).

## 7. Безопасность
- В тестах и логах не печатать секреты, токены, capability; `d` в access-логах nginx не писать
  (у нас `access_log off` на origin — сохранить).
- Никаких реальных секретов/доменов в репозитории, только `proxy.example.com` и тестовые векторы.
